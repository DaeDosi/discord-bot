# 치지직 통계 서비스 작업 정리

`/stats` 및 `/stats/streamer/[channelId]` 를 중심으로 진행한 작업을 한 문서로 모았다.
기능 목록이 아니라 **왜 그렇게 만들었는지와 다시 건드릴 때 주의할 점**을 남기는 것이 목적이다.
코드 구조 자체는 `CLAUDE.md`, 기능 명세는 `docs/기능_기술_정리.md`를 본다.

작성 시점: 2026-07-27 / 대상 브랜치: `main`

---

## 1. 서비스 개요

치지직 공개 라이브 목록을 약 10분 주기로 수집해 스트리머·카테고리·태그 단위로 집계해 보여 주는
비공식 통계 서비스다. 로그인이 필요 없는 공개 페이지이며, 애드센스 수익화 대상이기도 하다.

| 구성 | 위치 | 역할 |
| --- | --- | --- |
| 수집기 | `web/backend/rising_collector.py` | 치지직 라이브 목록 스냅샷 + 시간 롤업 + 오래된 데이터 정리 |
| 집계 API | `web/backend/routers/rising_router.py` | 모든 통계 엔드포인트(인증 없음) |
| 레이트 리밋 | `web/backend/rate_limit.py` | 공개 API 남용 방어 |
| 통계 페이지 | `web/frontend/app/stats/` | 좌측 메뉴 + 탭별 분석 화면 |
| 스트리머 상세 | `web/frontend/app/stats/streamer/[channelId]/` | 개인 대시보드(서브탭 6종) |

## 2. 데이터 파이프라인 — 다운샘플링이 이 서비스의 핵심 제약

### 왜 다운샘플링을 했는가

Railway 볼륨 한도가 **500MB**인데, 10분 원본 스냅샷을 14일 보관하면 실측 303B/행 기준으로
**약 3.25GB**까지 커진다. 그대로 두면 볼륨이 터진다.

그래서 **원본은 짧게, 롤업은 길게** 두는 구조로 바꿨다.

| 테이블 | 보관 | 단위 | 비고 |
| --- | --- | --- | --- |
| `rising_live_snapshots` | 약 26시간 | 라이브 1건 = 1행 | 태그·제목·팔로워 등 원본 필드 보유 |
| `rising_hourly_rollup` | 약 8일 | 채널 × 시간 = 1행 | 같은 시간의 6행 → 1행, 약 1/6로 축소 |
| `rising_collect_runs` | **영구** | 수집 사이클 = 1행 | 장기 트래픽 추이·히트맵의 유일한 장기 소스 |
| `rising_channel_stats` | **영구** | 채널 = 1행 | 원본을 자르면 사라지는 `first_seen`(데뷔일) 보존 |

결과적으로 예상 용량은 3.25GB → **약 468MB**가 됐다.

### 여기서 파생되는 제약 (중요)

- **8일 넘는 과거는 조회할 수 없다.** 화면에서 "지난 30일"을 골라도 실제로 집계되는 구간은
  롤업 보관 기간까지다. 새 기능을 만들 때 30일/90일 지표를 당연하게 가정하면 안 된다.
- **태그는 롤업에 없다.** 용량 때문에 컬럼을 늘리지 않았다. 태그 기반 필터는 원본(26시간)에서
  채널 집합을 뽑아 롤업에 적용하는 방식이라, 의미가 "최근 하루 안에 그 태그로 방송한 채널의 과거 추이"다.
- **다운샘플링 배포 전 백필이 필요하다.** 원본 14일 → 26시간 정리는 되돌릴 수 없으므로,
  기존 원본이 남아 있는 동안 롤업을 채워 두지 않으면 그만큼의 과거가 영구히 사라진다.
  **이 백필 스크립트는 아직 만들지 않았다.**

### 수집 범위

`PAGE_SIZE=50`은 치지직 API의 상한이라 더 올릴 수 없다. `MAX_PAGES`를 키워 4,000개 →
전체 라이브(측정 시점 약 5,717개, 치지직 전체 약 5,754개)를 모두 수집하도록 바꿨다.

## 3. 지표 정의

용어를 흔들지 않기 위해 정의를 고정했다.

- **뷰어쉽(시청 시간)** = 동시 시청자 × 방송 시간. `SUM(sum_viewers) × 10분 ÷ 60`으로 계산한다.
  `sum_viewers`는 "스냅샷 시청자의 합"이라 시간 단위로 환산해야 의미가 생긴다.
- **평균 동시 시청자** = 해당 구간의 시간 버킷 평균.
- **어떤 시각의 전체 동시 시청자** = 그 시각 방송 중이던 채널들의 `avg_viewers` 합.
  수집 주기(10분) 사이의 변동은 반영되지 않는다.
- **성장률** — 툴팁으로 산식을 그대로 노출한다. 값이 100%를 크게 넘는 경우(1위 1,800% 등)가
  흔해서, 프로그레스 바는 절대 스케일이 아니라 **상위 10명 내 min–max 상대 스케일 + 14% 하한**으로 그린다.
  절대 스케일로 두면 막대가 전부 꽉 차 보여 비교가 불가능했다.
- **신규(신입) 스트리머** — 시청자 하한 필터는 **제거했다**(3명 이상 조건이 있었음).
  대신 카테고리 표본 수 하한, 비피크 시간대 재계산, 티어 컷오프로 통계적 왜곡을 걸러 낸다.

## 4. 화면 구성

좌측 메뉴는 URL이 아니라 state로 전환된다(`StatsNav.tsx`). 그룹은 접이식이다.

| 그룹 | 탭 | 기준 |
| --- | --- | --- |
| 실시간 분석 | 전체 스트리머 분석 | LIVE(최신 수집 사이클 한 장) |
| | 신규 스트리머 분석 | LIVE |
| | **기간별 상세 분석** | 기간 누적 |
| 랭킹 | 전체 스트리머 랭킹 | LIVE |
| | 신규 스트리머 랭킹 | LIVE |
| | 기간별 누적 랭킹 | 기간 누적(100명 제한) |
| 카테고리 | 카테고리 분석 / 카테고리별 스트리머 / 태그 검색 | |

"실시간"과 "누적"은 성격이 완전히 다르다. 실시간은 그 순간 방송 중이었는지에 크게 좌우되고,
누적은 꾸준함이 반영된다. 그래서 한 그룹에 묶되 **LIVE 표시로 구분**한다.

### 스트리머 상세 페이지

프로필 배너 + KPI 4열 + 깃허브형 잔디 + 서브탭 6종 구조다.

## 5. 기간별 상세 분석 (신규)

다중 필터를 조합해 시계열 추이를 보는 대시보드. 좌측 280px 필터 패널 + 우측 분석 패널.

- **엔드포인트**: `GET /api/rising/period-analysis`, `GET /api/rising/period-filters`
- **컴포넌트**: `web/frontend/app/stats/PeriodAnalysis.tsx`
- **필터**: 기간(오늘/7일/30일/직접 지정) · 카테고리(검색 드롭다운) · 태그(멀티 칩, OR, 최대 8개) · 체급(라디오)
- **체급 구간**: 전체 / 신입·라이징(10명 이하) / 중소형(11~100) / 대기업(100 초과).
  기간 내 채널 **평균 동시 시청자**로 판정한다.
  `rising_router.py` 상단의 `TIERS`와 경계가 다른데, 저쪽은 실시간 체급 분포용이라 목적이 다르다.
- **출력**: 요약 카드 4종 · 이중축 추이 차트(시청자/채널/함께) · 시간대별 24칸 · 요일별 7칸 ·
  카테고리 정렬표(100개씩 페이지네이션)

### 설계 판단

- **필터는 "분석 적용"을 눌러야 반영된다.** 롤업 전 구간을 스캔하는 무거운 쿼리라
  필터를 만질 때마다 요청이 나가면 안 된다. `draft`/`applied` state를 분리하고,
  미반영 상태는 안내 문구로 표시한다.
- **시계열 묶음 단위는 자동**이다. 구간이 3일 이하면 시간 단위, 넘으면 일 단위.
- **이중축 차트는 `LineChart.tsx`를 쓰지 않고 전용 SVG로 그렸다.** `LineChart`는 Y축이 하나라
  시청자(수천)와 채널 수(수십)를 같은 축에 올리면 한쪽이 완전히 뭉갠다. 세 모드(시청자/채널/이중축)를
  한 구현으로 처리하기 위해 좌·우 축을 따로 가진 차트를 만들었다.
- **캐시 60초, 200개 상한.** 필터 조합이 사실상 무한이라 상한 없이는 메모리가 샌다.

## 7. 보안

- **SQL 인젝션 없음** — 모든 쿼리가 파라미터 바인딩이다. 문자열 포매팅으로 들어가는 부분은
  `WHERE` 절 조립뿐이고, 값은 전부 `?`로 분리했다. 실제로 `' OR 1=1--`을 카테고리로 넣어 확인했다.
- **채널 ID 검증** — 경로 파라미터가 외부 치지직 API URL에 그대로 붙기 때문에
  `^[0-9a-fA-F]{8,64}$`로 형식을 강제한다(경로 이탈 차단).
- **화이트리스트** — `tier`, `sort`, `range` 같은 열거형 값은 모두 딕셔너리 조회로 걸러
  알 수 없는 값이 오면 기본값으로 떨어진다.
- **개인정보 노출 없음** — 공개 라이브 목록 외의 데이터를 내려주지 않는다.

### 레이트 리밋 (`web/backend/rate_limit.py`)

슬라이딩 윈도우 60초, 프로세스 내 메모리 카운터(외부 의존성 없음).

- 일반 `150회/분`, 비싼 경로 `40회/분`
- 비싼 경로는 추측이 아니라 **실측 응답 시간**으로 골랐다:
  `newcomers` 3.9s / `streamer·detail` 4.4s / `ranking-period` 1.05s /
  `category-streamers`·`search`(외부 API 호출) / `period-analysis`
- 0.2초 이하인 `viewer-distribution`, `tags`, `tag-effect`, `traffic-heatmap`,
  `title-keywords`, `tag-streamers`는 제외했다.
- **처음에 비싼 경로를 20으로 잡았다가 자체 테스트에서 정상 사용자(새로고침 5회 + 전 탭 순회)가
  429에 걸렸다.** 사람이 1분에 낼 수 있는 양보다 넉넉하되 자동화 반복은 잡히는 선으로 40으로 올렸다.
- 인스턴스를 여러 개로 늘리면 Redis 같은 공유 저장소가 필요해진다.

## 8. 애드센스 대응

최초에 **"가치가 별로 없는 콘텐츠"**로 반려됐다. 원인은 로그인 게이트 뒤 빈 셸과 크롤 가능한 텍스트 부족이었다.

| 항목 | 조치 |
| --- | --- |
| 크롤 가능 텍스트 | `/stats` 263자 → **1,855자**, 스트리머 페이지 227자 → 약 1,300자 |
| FAQ | 766자 → **2,599자** (5문항 → 14문항, 통계 서비스 Q&A 9개 추가) |
| 메타데이터 | 페이지별 title/description, 스트리머는 채널별로 생성 |
| `ads.txt` | `web/frontend/public/ads.txt` |
| 사이트맵 | 정적 6개 + `/streamers-sitemap.xml`(동적, 1시간 ISR) |
| `robots.ts` | 로그인 게이트·알림 성격 경로 차단, 공개 콘텐츠는 크롤 허용 |
| 법적 링크 | 이용약관·개인정보처리방침 |

### 반드시 지켜야 할 것

- **`/stats`는 정적 프리렌더를 유지해야 한다.** 한 번 `useSearchParams()`를 넣었다가 Suspense 요구로
  정적 생성이 깨졌고, 그러면 크롤러가 빈 셸만 본다 → SEO 작업이 통째로 무효화된다.
  지금은 마운트 시점에 `location.search`를 직접 파싱한다.
- **canonical을 레이아웃에 두면 안 된다.** `/stats/layout.tsx`에 canonical을 넣었더니
  모든 스트리머 페이지가 `/stats`의 중복으로 취급돼 색인 자체가 막힐 뻔했다. 채널별 canonical로 바꿨다.
- 사이트맵의 스트리머 목록은 **롤업에 실제 방송 이력이 쌓인 채널만** 넣는다.
  데이터가 없는 페이지는 `layout.tsx`에서 noindex를 내보내므로, 넣어 봐야 색인 품질만 떨어진다.

## 9. 제거·보류한 것

- **스트리머 연관 관계망** — 만들었다가 사용자 요청으로 **전면 제거**했다. 되살리지 말 것.
- **호스팅(합방) 네트워크 지표** — 필요한 데이터를 수집하지 않아 산출 불가.
- **꾸준함 점수** — 14일 롤업이 필요한데 현재 8일이라 보류.
- **Turso 이전** — 비용 검토 후 "일단 다운샘플링, Turso는 나중에"로 결정.
- **산점도 휠 줌** — 페이지 스크롤을 막아서 제거했다. 확대/축소는 버튼으로만.

## 10. 다시 건드릴 때 유의할 점 (하드리 얻은 교훈)

1. **`range`를 FastAPI 파라미터 이름으로 쓰지 말 것.** 파이썬 내장 `range()`가 가려져
   함수 안에서 `range(24)`를 부르는 순간 500이 난다. 실제로 겪었다.
   쿼리 이름을 유지해야 하면 `Query("7d", alias="range")`로 받는다.
   (`ranking_period`는 `range()`를 안 써서 우연히 드러나지 않았을 뿐이다.)
2. **`HAVING`에서 집계 별칭을 쓰지 말 것.** `SUM(snaps) AS snaps` 후 `HAVING snaps >= ?`라고 쓰면
   SQLite가 집계값이 아니라 **원본 컬럼**으로 해석해 조건이 항상 거짓이 된다. `HAVING SUM(snaps) >= ?`로 쓴다.
3. **컴포넌트를 컴포넌트 안에 정의하지 말 것.** 렌더마다 새 타입이 되어 자식이 리마운트되고,
   내부 input은 한 글자 칠 때마다 포커스를 잃는다.
4. **React의 `onWheel`은 passive라 `preventDefault()`가 조용히 무시된다.** 필요하면
   `{passive:false}`로 네이티브 리스너를 붙여야 한다.
5. **`grep -c`는 매칭 개수가 아니라 줄 수를 센다.** 한 줄짜리 XML을 세다가 30개를 1개로 오판했다.
   개수를 세려면 `grep -o ... | wc -l`.
6. **좀비 `next start` 프로세스가 옛 빌드를 계속 서빙한다.** `pkill`과 `Stop-Process`가 조용히
   실패하는 경우가 있어 404를 실제 버그로 오진했다. `taskkill //F //PID <pid>`로 확실히 죽인다.
7. **`Switch.tsx` 토글과 라디오는 `<label>`로 감싸야 동작한다.** sr-only input이라
   스타일된 트랙만 눌러서는 아무 일도 일어나지 않는다.
8. **`grid-cols-24`는 Tailwind에 없다.** 임의값 문법을 써야 한다.
9. **SVG에는 z-index가 없다.** 겹침 순서는 그리는 순서로 정해진다. 툴팁이 가려지면 순서를 바꾸거나 포털을 쓴다.
10. **테스트용 백엔드를 띄우면 수집기가 실제 치지직 데이터를 테스트 DB에 밀어 넣는다.**
    `RISING_MAX_PAGES=0`으로 막지 않으면 시드 데이터와 섞여 검증이 무의미해진다. 실제로 한 번 당했다.

## 11. 검증 상태

- 기간별 상세 분석 백엔드는 시드 DB(채널 30 = 신입 6 / 중소형 14 / 대기업 10, 카테고리 5, 롤업 3,688행)로
  검증했다. 체급 분할 합계, 시간대 피크·최저 위치, 태그 OR 결과, 복합 필터, 잘못된 날짜 처리,
  화이트리스트 폴백, SQL 인젝션 시도, 캐시 동작이 모두 기대값과 일치했다.
- 프론트엔드는 `tsc --noEmit`과 `next build`를 통과했고 `/stats`의 정적 프리렌더가 유지됨을 확인했다.
- **브라우저 자동화 도구(playwright/puppeteer)가 없어 실제 클릭 동작은 검증하지 못했다.**
  필터 조작·차트 호버·정렬·페이지네이션은 수동 확인이 필요하다.
- 이 저장소에는 테스트 스위트·린터·CI가 없다. 변경 후 실행할 자동 검사는 존재하지 않는다.

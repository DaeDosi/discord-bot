## 2. 사고 1 — `/main` 호출 폭주와 Egress 비용

### 실측 (2026-07-30)
- `/api/singcup/main?limit=3000` 응답: 원본 **약 868KB**, gzip **약 265KB**
- 호출량: **분당 34.9~63회** (구간에 따라)
- 방문자 약 100명 → 1인당 약 3.85회/10분
- Railway Estimated Usage **$41.86** 중 **Network Egress $38.15** (약 763GB/월 추정)
- **`/main`이 관측 구간 Egress의 약 95%** (나머지는 `/rising/*`)

### 밝혀진 원인 (추측 아님)
1. 폴링 60초 × 화면 2개 × 탭 수, hidden 탭도 계속 호출 → `aa11222`로 5분·hidden 중단
2. **ETag/304는 정상 동작하지만 효과가 거의 없다** — 로그 745회 중 304는 1회(0.13%).
   이유: 200초 간격으로 두 응답을 비교했더니 **하트/조회수가 실제로 바뀐 사람은 52명(4.8%)인데
   `rank`는 802명(74.3%)이 바뀐다.** `compute_scores`의 분모가 전체 최댓값이라 소수의 변화가
   전체 순위로 증폭된다. 즉 이 응답은 **구조적으로 캐시 친화적이지 않다.**
3. 브라우저는 `max-age` 안에서는 캐시를 쓰지만, 만료 후에는 조건부 요청 없이 전량 재수신하는
   경우가 관측됐다. 또 `Access-Control-Expose-Headers: ETag`가 없어 **JS가 ETag를 읽을 수 없다**
   (수동 조건부 요청 구현 불가).
4. 브라우저 → **Railway 직접 호출**이라 사용자 사이에 공유 캐시가 전혀 없다(Vercel 경유 아님).

### 결론
**행 수를 줄이는 것(분리 API)만이 실질 해법이다.** 필드 슬림화는 gzip 기준 −2.7%뿐이고,
CDN은 Railway Egress를 Vercel Fast Data Transfer로 **옮길 뿐** 총 전송량은 그대로다.

## 3. 사고 2 — 1시간 증감 전면 붕괴 (`057731b`로 수정)

### 증상 (2026-07-30 20:5x 실측)
참가자 1,060명 중 **`isNew`가 1,057명**, `heartDelta` null 1,057, `topHeartMovers1hStale=true`,
**기준선 행 수 7**.

### 원인
`_save_snapshots`는 `UNIQUE(event_id, owner, snapshot_bucket)` + `INSERT OR IGNORE`라
**같은 시간대의 두 번째 저장에서 기존 참가자가 전부 무시되고 그 사이 새로 들어온 참가자만**
새 `collected_at`으로 들어간다. 그런데 `find_reference_run`이 **collected_at 한 점을 회차 ID로**
골랐고 `_delta_maps`가 그 시각과 정확히 일치하는 행만 읽어, **7명짜리 부분 세트가 기준선**이 됐다.

### 수정
회차의 단위를 **시간 버킷**으로 바꿨다(`find_reference_baseline`). 버킷은
`COALESCE(snapshot_bucket, (collected_at/3600)*3600)`로 잡되 후보는 `collected_at` 범위로 좁혀
기존 인덱스를 탄다 — **마이그레이션도 데이터 변경도 없고, 기존 부분 세트는 조회만으로 복구된다.**

추가로 넣은 것:
- **허용 오차가 커버리지보다 우선**. coverage가 정상이어도 target에서 멀면 쓰지 않는다.
- 불완전 판정 기대치 = **더 오래된 후보 버킷들의 최대 인원**(참가자 수 단조 증가 이용).
  임계값 `SINGCUP_BASELINE_MIN_COVERAGE` 기본 **0.9**.
- 기준값 없음의 이유를 나눔: `new` / `baseline_incomplete` / `insufficient_history` /
  `representative_changed` / `recovering` / `ok`. **NEW는 `first_collected_at > 기준 시점`일 때만.**
- 관리자 진단 `GET /api/singcup/snapshots/baseline` (45초 캐시 + single-flight + timeout)

|---|---|---|---|---|---|---|
| 1 | 22:27:34 | 21:00 | 1,070/1,061 | false | false | 5 |
| 2 | 22:33:35 | 22:00 | 1,071/1,070 | false | false | 5 |

## 4. 분리 API (백엔드) — `037400e` + `30ae107`

### 엔드포인트 (전부 `SINGCUP_SPLIT_API_ENABLED=true`일 때만 열림)

| 경로 | 응답 | 실측 gzip |
|---|---|---|
| `GET /api/singcup/summary` | KPI·movers·live·collector + `summaryVersion` | **2,045 B** |
| `GET /api/singcup/rankings-page` | `size/cursor/sort/direction/snapshotVersion` | **28,204 B**(100명) |
| `GET /api/singcup/search` | 전체 집합 검색 | 6,012 B(20명) |
| `GET /api/singcup/live` | 방송 중만 | 15,467 B(50명) |
| `GET /api/singcup/movers` | 급상승 + `moversVersion` | 1,641 B |
| `GET /api/singcup/delta` | **미구현** — `not_available` 고정 | — |
| `GET /api/singcup/snapshots/registry` | 관리자(secret) | — |

> **경로 이름 주의**: `/api/singcup/rankings`는 **이미 자유게시판 홍보글**이 쓰고 있다.
> 그래서 새 랭킹은 `/rankings-page`다. 덮으면 그 화면이 깨진다.

### 반드시 지켜야 할 설계 (되돌리지 말 것)

1. **정렬·검색은 언제나 전체 참가자 집합 기준.** 받아온 100명 안에서 다시 정렬/검색하면
   하위권이 사라지고 순위가 왜곡된다. `limit=3000`을 줄이는 방식도 같은 이유로 금지.
2. **오름차순은 `reverse()`가 아니다.** 방향은 주 키에만 적용하고 동점 기준
   (하트↓ → 점수↓ → channelId↑)과 null 위치(항상 뒤)는 두 방향에서 같다.
3. **`snapshotVersion`은 랭킹 집합만의 지문**이다. `/main` ETag를 재사용하면 집계 시각처럼
   페이지네이션과 무관한 변화로 커서가 죽는다.
4. **`summary`/`movers`는 랭킹 스냅샷이 아니라 최신 봉투에서 읽는다.** 랭킹에 얼려 두면
   `ranking_version`이 같다는 이유로 새 스냅샷이 등록되지 않아 **과거 값으로 굳는다**(실측 확인).
   각자 `summaryVersion`/`moversVersion`을 낸다.
5. **스냅샷은 등록 시 복사해 고정한다**(`_freeze`). 원본 dict를 참조만 하면 나중에 바뀌었을 때
   이미 발급한 버전의 내용이 조용히 달라진다.
6. **커서에는 버전·엔드포인트·필터 해시·정렬·방향·마지막 키를 함께 서명**한다.
   서명은 **hex**로 붙인다 — 원시 바이트면 서명 안에 `.`이 들어가는 경우가 약 4.5% 생겨
   멀쩡한 커서가 거부된다(테스트로 잡음).
7. **생산자는 조회 경로와 분리한다.** `recompute_ranking()` 완료 직후 + 기동 warm-up에서만
   `publish_snapshot()`이 돈다. 조회는 메모리만 읽고, 스냅샷이 없으면 **503**을 준다
   (만들려면 `/main` 계산 → `_save_top_movers` DB 쓰기를 타게 된다).
8. **게시 경로는 DB에 쓰지 않는다**(`persist_top_movers=False`). 매번 같은 값을 다시 UPDATE하면
   P1에서 없앤 잠금 경합이 되살아난다.
9. **응답 bytes를 캐시한다**(`render()`, LRU 128). 이걸 넣기 전에는 요청당 재직렬화 때문에
   분리 API가 `/main`보다 느렸다(1,079명 p50 3.1ms → 7.2ms).

### 보존 정책
- `SINGCUP_SNAPSHOT_MIN_SESSION_SECONDS=900` **우선 보장**
- `SINGCUP_SNAPSHOT_MAX_VERSIONS=60`, `SINGCUP_SNAPSHOT_MAX_ITEMS=60000`(약 57MB) — 메모리 상한
- 상한에 걸려 축출되면 클라이언트는 **409 → 처음부터** (API 계약에 명시, `retentionSeconds` 노출)

| 참가자 | 스냅샷 1개 | 실제 보존 |
|---:|---:|---:|
| 1,081(현재) | 1.04 MB | **15.0분** |
| 5,000 | 4.74 MB | 4.0분 |
| 10,000 | 9.47 MB | 2.0분 |

> 10,000명에서 15분을 보장하려면 **세대별 전체 복사 대신 변경 없는 레코드 공유**나
> **랭킹 최소 필드만 tuple 보관**으로 재설계해야 한다. 현재 규모에서는 문제없다.

## 7. 활성화 전 반드시 할 것

1. **Railway에 secret 2개를 서로 다른 값으로 설정** (값은 문서·로그에 남기지 말 것)
   - `SINGCUP_ADMIN_SECRET` — **현재 미설정**이라 관리자 진단이 전부 503이다.
     그래서 `/api/singcup/observability`(분당 호출 수·bytes·캐시 적중)를 아직 한 번도 못 봤다.
   - `SINGCUP_CURSOR_SECRET` — 최소 32바이트 무작위. 16자 미만이면 분리 API가 **켜지지 않는다**.
2. 프론트 UI 배선 완료 + 실브라우저 검증
3. **백엔드 플래그 먼저** 켜고 curl로 6개 경로 확인 → 그 다음 프론트 플래그
4. 배선과 플래그 활성화를 **같은 커밋·같은 배포에 넣지 말 것**

## 9. 하지 말 것 (되돌리기 금지)

- `limit=3000` 축소 — 하위권 검색·정렬이 통째로 깨진다
- 페이지 안에서 다시 정렬·검색

- `snapshotVersion`을 `/main` ETag로 되돌리기

- 조회 경로에서 스냅샷 생성 / 게시 경로에서 `_save_top_movers` 호출
- 60초 폴링 복귀, hidden 폴링 재개
- 스윕 정각 스케줄 회귀, `is_rep DESC, heart_count DESC` 정렬 복귀 (이전 문서 참조)
- 커서 서명을 원시 바이트로 붙이기

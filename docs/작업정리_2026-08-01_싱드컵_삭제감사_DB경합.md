## 2. Change Set B / B2 / B2.1 요약

### 무엇을 고쳤나

삭제된 클립이 대표로 남아 순위가 굳는 문제. 근본 원인은 **삭제 여부의 유일한 권위인
상세 API(`/service/v1/clips/{uid}/detail`)를 `suspected_deleted` 행에만 물었고,
의심으로 들어가는 문이 스윕의 카드 API 실패 하나뿐**이었던 것. 카드는
`seedMediaId=videoId`로 조회하고 **원본 VOD는 클립 삭제 후에도 남으므로**, 카드가
정상 응답하는 삭제 클립은 확인을 못 받았다.

B2가 그 사각지대를 메운다: **카드 상태와 무관하게 모든 활성 클립을 목표 커버리지
시간(기본 12시간) 안에 한 번씩 상세 API로 확인**한다.

### 절대 되돌리면 안 되는 규칙

- **힌트는 삭제 근거가 아니라 우선순위다.** 새 형제 클립·대표 교체·카드 결측·
  지표 장기 고정 — 어느 것으로도 `active`/`deletion_state`를 바꾸지 않는다.
- **확정은 서로 다른 시점의 명시적 404 2회.** `DELETION_MIN_INTERVAL_SECONDS`(10분)
  이상 간격. 429·5xx·timeout·형식 오류는 `inconclusive`이고 확인 횟수에 넣지 않는다.
- **404는 의미까지 본다.** Content-Type이 JSON이고 본문 `code`가 404인 것만 인정.
  경로 오타·프록시가 준 HTML 404를 삭제로 확정하면 멀쩡한 클립이 사라진다.
- **410은 삭제 근거가 아니다.** 이 API에서 관측된 적이 없어 `http_410_unverified`로
  세기만 한다. 실제 410을 관측하면 그때 의미를 확인하고 규칙을 정한다.
- **확정 + 대표 재선정은 한 트랜잭션**, 전용 연결, rowcount 불일치 시 커밋 안 함.
- **진행 상태는 `singcup_clips.audit_next_at`이 곧 커서.** 별도 진행률 표·offset
  페이지네이션을 만들지 말 것(행이 밀리면 건너뛰기와 중복을 동시에 만든다).
- **결정적 jitter는 `sha256(clip_uid)`.** 내장 `hash()`는 프로세스마다 달라 재시작
  때 순서 편향이 생긴다(AST 테스트로 고정).
- **UID 하드코딩 금지.** `_code_only()`가 주석·문자열을 걷어낸 실행 코드에서 검사한다.

### 플래그 진리표 (테스트로 고정)

| ENABLED | SHADOW | HOT | COLD | 힌트 쓰기 | 상세 API | 운영 상태 변경 |
|---|---|---|---|---|---|---|
| false | * | * | * | ✗ | ✗ | ✗ |
| true | true | false | false | ✓ | ✗ | ✗ |
| true | true | true | false | ✓ | Hot | ✗ |

않는다 — Phase 1에서 두 레인을 보려면 넷 다 명시해야 한다.

## 4. **커밋 대기 중** — DB 쓰기 경합 개선

### 문제

백엔드는 **하나의 공유 aiosqlite 연결**을 쓴다. 연결마다 워커 스레드가 하나라
모든 작업이 그 큐에서 직렬화된다. 긴 쓰기 하나가 공개 조회까지 통째로 뒤로 민다.

실측(Railway):

```
13:11:16 UTC  rising_collector 프로필 20,963행 저장
13:12:19 UTC  chzzk_monitor: database is locked
같은 시각     GET /api/singcup/main 10,298ms
12:26 UTC     db_locked_giveup what=acquire_owner_lock (rising와 6분 떨어짐)
```

**원인을 하나로 확정하지 말 것.** 여러 writer의 복합 경합이고, 아래가 각각 기여한다.

| 경로 | 프로세스 | 연결 | 문제 |
|---|---|---|---|
| `recompute_ranking` | 백엔드 | 공유 | 참가자 수만큼 `_upsert_streamer`를 await, **중간 COMMIT 없음** |
| `rising_collector._persist_profiles` | 백엔드 | 공유 | 2만 행 UPSERT + DELETE 한 트랜잭션(일 1회) |
| `chzzk_monitor._check_once` | 백엔드 | 공유 | 알림 전송 중에 쓰기 트랜잭션이 열려 있음 |
| `chzzk_chat._mark_synced` | **봇** | 공유(봇) | 재시도·rollback 없음 → 예외가 동기화 루프를 끊음 |
| `singcup_retention` dry-run | 백엔드 | 공유 | 읽기 전용이지만 81만 행 집계 18.5초, 매번 재실행 |

로그 위치 확인: `"프로필 이미지 N개 DB 저장"`은 **COMMIT 이후**에 찍힌다. 즉
그 로그 시각에는 이미 잠금이 풀려 있다 — 로그 시각만으로 원인을 잡으면 틀린다.

### 벤치마크 (로컬, 운영과 같은 함수·상수)

`recompute_ranking` 쓰기 방식 비교. **트랜잭션은 두 방식 모두 하나**다.

| 방식 | 참가자 | 소요 | 실제 쓴 행 | 동시 writer 성공률 |
|---|---|---|---|---|
| A 반복 UPSERT(기존) | 1,130 | 249ms | 1,130 | 100% |
| **C 바뀐 행만 executemany** | 1,130 | **8ms** | **0** | 100% |
| A 반복 UPSERT(기존) | 4,000 | 827ms | 4,000 | **50%** (locked 1건) |
| **C 바뀐 행만 executemany** | 4,000 | **25ms** | **0** | **100%** |
| C (1% 실제 변경) | 1,130 / 4,000 | 7ms / 25ms | 11 / 40 | — |

별도 벤치(`scratchpad/bench_lock.py`)에서 4,000명 규모의 A 방식이
`acquire_owner_lock`(전용 연결, busy_timeout 500ms×2, 예산 1.0s)을 실제로
`database is locked`로 만드는 것을 재현했다.

### 선택한 방식과 이유

**C — 값이 바뀐 행만 골라 `executemany` 한 번 + COMMIT 한 번.**

중간 COMMIT은 쓰지 않는다. 쪼개면 일부 스트리머만 새 랭킹인 상태가 사용자에게
보이고, 중단되면 그 혼합 세대가 **영구히** 남는다. 줄이는 대상은 트랜잭션 개수가
아니라 **한 트랜잭션이 쓰는 양**이다. 대부분의 회차에서 실제로 바뀌는 행은 0~수십 개다
(예전에는 `row_updated_at = excluded.row_updated_at` 때문에 매번 전원이 바뀌었다).

같은 원리를 프로필 저장에도 적용했다 — 이미지 URL은 거의 바뀌지 않으므로
바뀐 행만 UPSERT하고, 나머지는 `updated_at`만 밀어 30일 정리에 걸리지 않게 한다.
갱신과 정리(DELETE)는 **한 트랜잭션**으로 둔다(갈라지면 중단 시 '지웠는데 갱신은
안 된' 상태가 남는다).

### 부분 랭킹 방지를 어떻게 보장하나

- `_upsert_streamers_bulk`는 **스스로 커밋하지 않는다**(테스트로 고정)
- `recompute_ranking`의 `await db.commit()`은 **정확히 1개**(테스트로 고정)
- 커밋 전 중단 시 아무것도 반영되지 않는다(rollback 테스트)
- 주의: 백엔드는 공유 연결 하나를 쓰고 SQLite 커서는 지연 평가라, **같은 연결에서**
  읽으면 자기 쓰기가 보인다(read-your-own-writes). "절대 섞여 보이지 않는다"는 이
  구조에서 성립하지 않는다. 성립하는 것은 ① 커밋 안 된 결과는 남지 않는다
  ② 노출 창이 반복 UPSERT보다 훨씬 짧다 — 테스트가 이 둘을 잰다.

## 7. 관측·진단 방법

```bash
B=https://discord-bot-production-4bae.up.railway.app
curl -s "$B/api/singcup/audit/status"   | python -m json.tool   # 감사 상태(공개)
curl -s "$B/api/singcup/sweep/status"   | python -m json.tool   # 스윕 진행률(공개)
curl -s "$B/api/singcup/streamers/<channelId>/clips"            # active=1 클립만
```

`GET /api/singcup/main?limit=3000`은 약 900KB다 — **조사용으로도 자주 부르지 말 것**
(전송비가 곧 비용). 레이트 리밋은 기본 150 req/60s, `/main` 계열은 40 req/60s이라
전 채널 스캔은 초당 2건 이하로 페이싱해야 한다(넘기면 내 요청이 429를 받는다).

`active=0`을 판정하는 공개 대리 지표: `/streamers/{cid}/clips`는 `active=1`만
반환하고, `singcup_clips.active`를 0으로 바꾸는 문장은
`_confirm_deleted_and_reselect` 하나뿐이며 같은 UPDATE가
`deletion_state='confirmed_deleted'`를 함께 쓴다. **목록에서 사라지면 곧 확정 삭제다.**

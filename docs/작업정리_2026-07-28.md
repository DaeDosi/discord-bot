## 1. 버그 수정

### 1-1. 싱드컵 참가자가 검색되지 않던 문제

**증상**: 특정 스트리머를 닉네임으로 정확히 입력해도 "없습니다"가 뜸.

**원인**: 검색은 서버에 질의하지 않고 `/api/singcup/main` **응답 안에서만** 필터링하는데,
화면이 `limit=200`으로 상위 200명만 받아왔다. 참가자가 535명이라 **201위 이하는 구조적으로
검색 불가**였다. 헤더에는 "참가 스트리머 535명"이라고 표시되면서.

**수정**
- `load_main` 상한 500 → 3000, 화면은 전원 요청
- 전원을 한 번에 그리면 무거우므로 목록만 나눠 표시(검색·정렬은 항상 전체 대상)
- 싱드컵 라이브 페이지도 동일 — 라이브 여부는 순위와 무관한데 상위 200명만 보고 있었다

**부수 발견**: 랭킹 계산이 닉네임을 채널 API에서만 가져와, 그 호출이 실패하면 이름이 빈
문자열이 되어 화면에 `-`로 뜨고 검색에 영구히 안 걸렸다. 클립 목록 응답에 이미 있던
`ownerChannel`을 저장해 폴백으로 쓰도록 수정. 팔로워 787건 순차 조회도 병렬로 전환.

### 1-2. 랭킹 요약 차트 툴팁 잘림 (전체·신규 랭킹 공통)

**원인**: **z-index 문제가 아니었다.** 카드의 접기/펼치기 애니메이터가
`overflow:hidden` + `max-height`로 clipping context를 만들고 있었고, 툴팁은 그 안의
`absolute` 요소였다. clipping context 안에서는 z-index를 아무리 올려도 빠져나갈 수 없다.
(`.card` 자체에는 `overflow`가 없어 카드가 원인이 아니었다.)

**수정**: `document.body`로 Portal + `position:fixed`. 컨테이너의 `overflow`는 건드리지
않아 둥근 모서리·막대 애니메이션·레이아웃이 그대로다.
- 아래 배치 기본, 공간이 모자라면 위로 뒤집고, 위도 모자라면 넓은 쪽으로 clamp
- 좌우도 뷰포트 기준 clamp / `pointer-events:none`(깜빡임 방지) / scroll·resize 재계산
- 터치: 탭하면 열리고 패널 바깥을 누르면 닫힘

### 1-3. 히트맵 / 막대그래프 툴팁이 늦게 뜨던 문제

네이티브 `title` 속성이라 브라우저가 1~2초 가만히 둬야 띄웠다. 직접 그리는 툴팁으로 교체.
`BarBlock` 하나를 '시간대별 평균 시청자'와 '요일별 트래픽 분포'가 공유하므로 동시 적용.

### 1-4. 그 외

| 문제 | 원인 / 수정 |
|---|---|
| 1위 막대만 짧아짐 | 우측 지표 칸이 `min-width`라 여섯 자리 행만 넓어져 `flex-1` 트랙이 짧아졌다 → 폭 고정 |
| 모바일에서 막대 소멸 | 고정폭 합이 카드 폭을 넘어 트랙이 0px → 반응형 폭 + `min-w` |
| 태블릿(~820px) 가로 넘침 45px | 행이 `sm`부터 `nowrap` → `lg`부터 한 줄 배치 (기존 문제) |
| `0.0%`가 상승 초록 | `deltaPct >= 0`을 전부 상승 처리 → 중립색 분리 |
| '마지막 집계'가 두 개 | 수집기가 다른 두 시각이 같은 이름 → '라이브 집계'/'싱드컵 집계'로 분리 후, 싱드컵 탭에서는 헤더 쪽을 숨김 |

## 2. 신규 기능

### 2-1. 전체 동시 시청자 추이 — 48h / 72h

`rising_collect_runs`는 프루닝하지 않으므로 **추가 수집 없이** 바로 가능했다.
`collected_at`의 UNIQUE 자동 인덱스로 범위 스캔이 처리되어 **새 인덱스도 불필요**
(26,000행 실측 0.5ms).

| range | 창 | 버킷 | 포인트 |
|---|---|---|---|
| live | 24h | 원본 10분 | 144 |
| 48h | 48h | 30분 평균 | 96 |
| 72h | 72h | 1시간 평균 | 72 |

- `range`를 `Query(pattern=...)`로 검증 → 오타는 422. 기존엔 조용히 24h로 떨어졌다
- **정상 완료 사이클만** 포함: `ok=0`, `live/viewers=0`, 그리고
  `note='page_cap_reached'`(목록이 잘린 부분 성공 — 과소 집계라 가짜 급락을 만든다)
- 공백은 0으로 메우지 않고 포인트를 비운 뒤 `step_seconds`로 프론트가 **선을 끊는다**
- 미완성 마지막 버킷은 점선 + 속 빈 점으로 '집계 중' 표시
- 이력이 짧아도 버튼을 막지 않고 "현재 수집 이력 N시간" 안내

### 2-2. 싱드컵 — 최근 1시간 하트 급상승 Top 5

백엔드가 `topHeartMovers1h`로 집계해 내려준다(프론트 재계산 금지).

- 스트리머당 **현재 대표 클립 하나만**. 여러 클립 합산 금지
- **대표 클립이 바뀌었으면 제외** — 다른 영상끼리 빼면 증가량이 통째로 가짜다
- `heartDelta1h > 0`이고 양쪽 스냅샷이 모두 있는 경우만. NEW 제외
- 동률: 현재 하트 → 점수 → channelId
- UI: 다색 `conic-gradient` 회전 테두리(7초/바퀴, `::before`만 회전해 내용은 안 돌고
  레이아웃도 안 흔들림), Top1만 강조, `prefers-reduced-motion`에서 회전만 정지

### 2-3. 싱드컵 KPI 증감

```
4,324 개  ▲47
60분 전 대비
```

**비교 기준을 배열의 이전 값이 아니라 "기준 시각(now−1h) ±15분 안의 실제 수집 회차"** 로 잡는다
(`find_reference_run`). 회차 하나를 고르면 그 시점의 순위·점수 기준이 통째로 일관되고,
수집이 멈춰 있던 구간에서 며칠 전 값과 비교해 놓고 '1시간'이라 표시하는 일이 없다.
기준 회차가 없으면 **0이 아니라 `null` → "비교 데이터 없음"**.

## 3. 수집기 / 데이터 품질

### 3-1. 수집 사이클 계측 + 시작 간격 고정

주기를 600→300초로 줄여도 되는지 물었을 때 **세 조건을 확인**한 결과:

| 조건 | 결과 |
|---|---|
| `streamerCount`가 고유 채널 수인가 | ✅ `singcup_streamers` PK가 `channel_id` |
| 루프가 고정 간격인가 | ❌ **'완료 후 대기'였다** → `sleep(INTERVAL - elapsed)`로 수정 |
| p95가 주기보다 짧은가 | ❌ **측정 자체가 불가능했다** |

`rising_collect_runs`에 소요시간도 호출 수도 없었다. → `duration_ms` / `pages` /
`api_calls` 추가하고 `/api/rising/status`에 `cycle_24h`(p50/p95/max, 평균 호출 수,
`safe_to_halve` 판정) 노출.

**`RISING_COLLECT_INTERVAL`은 변경하지 않았다.** 24시간 측정 후 `safe_to_halve: true`를
확인하고 결정할 것.

### 3-2. 급상승 점수 공식 (`web/backend/rising_score.py`)

기존은 단일 스냅샷 × 순수 퍼센트 정렬이라 **1명→8명(+700%)이 200명→300명(+50%)을
언제나 이겼다.**

- `window_median` — 시간 구간 중앙값. 표본 부족이면 `None`(0 아님).
  **행 개수를 가정하지 않아** 수집 주기가 5분으로 바뀌어도 동작
- `raw_growth_rate`(화면용) / `adjusted_growth_rate`(랭킹용, 분모 하한 20) 분리
- `rising_score = max(delta,0) × log2(2 + cur/max(base,20)) × 유지계수 × 신뢰도`
- 7개 상태값. 작은 채널은 배제가 아니라 `NEW_BREAKOUT`으로 분리
- 신규 급부상은 **퍼센트로 정렬하지 않음**(절대 증가량 우선)

**⚠️ 아직 엔드포인트에 연결하지 않았다** — 5절 참고.

## 5. DB 진단 및 안전장치

### 5-1. 진단 결과

프루닝이 걸린 테이블은 셋뿐이었다(`rising_live_snapshots`, `rising_hourly_rollup`,
`channel_profiles`). **`singcup_snapshots`는 완전히 무제한이었다.**

로컬에서 20만 행을 실제로 넣어 측정:

```
200,000행 = 37.9MB  →  행당 198 bytes (인덱스 2개 포함)
참가자 800명 × 4분 주기 = 288,000행/일 = 55MB/일
21일 이벤트 = 6,048,000행 = 1,145MB   ← 500MB 볼륨의 2.3배
```

### 5-2. 보존정책 (`web/backend/singcup_retention.py`)

원본을 읽는 코드를 전부 확인한 결과 가장 멀리 소급하는 것은 `_delta_maps`의
24시간 비교였다. **그보다 오래된 원본을 읽는 코드는 없다.**
→ 원본 26시간, 그 이전은 시간당 1행 롤업 → 일별 압축 → 최종 성적 영구 보존.

**예상 절감: 55MB/일 → 원본 약 60MB 고정 + 롤업 3.7MB/일 (약 93%)**

### 5-3. ⚠️ 프루닝은 파괴적이며 현재 비활성

> **코드를 revert해도 이미 삭제된 원본은 복구되지 않는다.**
> 스키마 추가는 되돌릴 수 있지만 데이터 삭제는 되돌릴 수 없다.
> 이 둘을 묶어 "append-only 변경"이라고 부르면 안 된다.

**백업이 아직 없으므로 기본값에서 한 행도 지우지 않는다.**

| 안전장치 | 내용 |
|---|---|
| 기본 비활성 | `SINGCUP_SNAPSHOT_PRUNE_ENABLED=false` |
| 이중 관문 | `ENABLED`와 `DRY_RUN` 둘 다 넘어야 삭제 |
| 롤업 검증 | 원본의 스트리머가 롤업에 하나라도 빠지면 그 시간대 삭제 금지 |
| 결정적 대표값 | `(collected_at DESC, id DESC)` + UNIQUE 제약 → 재실행이 UPSERT |
| 배치 커밋 | 배치마다 COMMIT + sleep. 소요시간·삭제 건수·lock 재시도·WAL 크기 로그 |
| 삭제 상한 | 1회 `PRUNE_MAX_ROWS`까지 |
| 최종 성적 | 어떤 압축 단계에서도 건드리지 않음 |

활성화 절차는 [`SNAPSHOT_RETENTION.md`](./SNAPSHOT_RETENTION.md) 참고.

### 5-4. 진단 엔드포인트 / 보안 / SQLite 튜닝

- `GET /api/admin/db/diagnostics` (오너 전용) — 파일·WAL·SHM 크기, 페이지 통계,
  회수 가능량, 테이블별 행 수와 1h/24h/7d 증가량, **측정값 기반** 예상 소진일,
  **"프루닝 없는데 증가 중"인 테이블 목록**. 10분 캐시 + 동시 실행 1개 + 타임아웃
- `GET /api/admin/db/integrity` — 기본 `quick_check`, `?full=true`는 백업 후 검증용
- `GET /api/admin/db/retention/report` — dry-run 리포트
- **보안**: `start.sh`가 `DATABASE_URL` 전체를 배포 로그에 출력하고 있었다. 지금은 SQLite
  경로라 무해하지만 PostgreSQL로 옮기면 비밀번호가 남는다 → 마스킹
- **SQLite**: `busy_timeout`이 **기본값 0**이라 잠긴 순간 즉시 실패했다 → 10초,
  `synchronous=NORMAL`, `wal_autocheckpoint=1000`

## 6. 남은 작업

### 결정이 필요한 것

**① 급상승 규모 상한** — `rising_score.py`는 완성됐지만 엔드포인트에 연결하지 않았다.
절대 증가량이 뼈대라 상한이 없으면 상위 10 중 8건이 대형 채널이 된다(실측).
기존 `rising-stars`는 `현재 1000명 미만`만 대상으로 했고(코드 주석: "라이징 취지(중소형
급상승)"), 그 상한을 유지하면 상위권이 `167→415(+148%)` 같은 중형 급상승이 된다.

| | 상한 없음 | 기존 상한 유지 |
|---|---|---|
| 상위 10 중 대형 | 8건 | 0건 |
| 1위 | 3,838→4,717 (+22.9%) | 167→415 (+148.5%) |

→ **권장: 기존 상한 유지.** 제품 의도라 임의로 정하지 않음.

**② 프루닝 활성화** — 백업 완료 + dry-run 결과 확인 후 결정.

### 미착수 (규모가 커서 분리)

- **P0 나머지**: `/api/rising/rising-stars` 재작성(중앙값·세션 판별·상태값·두 그룹),
  24시간 비교 중앙값화, `뷰어쉽` → `추정 시청시간` 명칭 수정, 기회지수,
  히트맵 0/데이터없음 구분
- **P1**: 시장 기회 분석, 시청자 집중도, 제목 키워드 개선, 개인 분석 연결
- **DB 후보 비교 / PostgreSQL 이전**: 진단 엔드포인트를 24시간 돌린 실측 수치가 있어야
  의미가 있다
- **`rising_live_snapshots` 정규화**: 채널명·제목이 매 수집마다 중복 저장. 이미 26시간
  프루닝이 있어 급하지 않고, 세션 테이블 설계가 Postgres 이전과 겹친다

### 데이터 확인 필요

화면의 태그 클립 529개 / 참가 스트리머 151명이 이전 백필 실측(4,032클립 / 787명)과
차이가 크다. 이벤트 기간은 `singcup_collector.START_AT/END_AT` 단일 상수이고 백필과
정기 탐색이 같은 조건을 쓰는 것은 확인했다.
→ `GET /api/singcup/clips/backfill/status`로 백필 상태(`completed` / `paused` / `failed`)
먼저 확인 필요. **임의로 재수집하거나 데이터를 지우지 않았다.**

### 알려진 제약

- **원본 26시간 / 롤업 8일** 보관이라 원본 기반 7일 분석은 불가, **14일 기간은 용량상
  불가**(실측 원본 26h=258MB + 롤업 8일=210MB ≈ 468MB, 한도 500MB)
- **팔로워는 상위 100채널만 보강**되어 하위 채널은 0
- **방송 종료 시각 없음** — 스냅샷에서 사라지면 종료로 추론
- **세션 식별자 없음** — 단, `rising_live_snapshots.open_date`로
  `(channel_id, open_date)` 조합 판별이 가능해 스키마 변경은 불필요
